
本文用于识别传统项目智能化（Agentification）过程中可能出现的主要风险，并概述主要化解方向。分类按风险类型组织，便于讨论和识别相关风险。表格中“风险”描述可能出现的问题，“简要说明”说明其表现或影响，“主要化解方向”仅指出关键控制思路，这里不展开具体机制。

## 一、AI 业务价值与流程影响

| 风险 | 简要说明 | 风险化解方向 |
|---|---|---|
| 为了 AI 而 AI | 引入 Agent，却没有解决明确的用户或业务问题。 | 从具体业务痛点和目标用户出发；定义可衡量的收益指标与停止条件。 |
| 业务价值无法度量 | 使用量、模型效果或演示表现不能证明业务结果得到改善。 | 建立上线前基线；持续衡量任务完成率、耗时、返工、成本和用户反馈。 |
| 自动化了错误流程 | 在未理解现有流程和责任的情况下，用 AI 加速低效或不合理的流程。 | 先梳理业务流程、例外和决策权，再确定哪些环节值得重构或自动化。 |
| Agent 化范围过大 | 从局部辅助直接跳到端到端自主执行，带来质量、安全失控风险。 | 按业务价值和风险分阶段扩大范围；每阶段设适用边界、验收标准和退出条件。 |
| 传统能力被 AI 取代或遮蔽 | 常规任务必须经过 AI，或用户失去熟悉、确定的操作路径。 | 保留传统交互和确定性流程；通过明确的请求路由让不同请求进入合适处理路径。 |
| 用户不信任或不采用 | 用户无法理解 AI 的能力边界或结果依据，因而不愿使用。 | 让能力边界和结果依据对用户清晰可见，并保留反馈与纠正渠道。 |
| 用户过度依赖 AI | 用户将 AI 输出视为确定事实或专业决策，忽视验证和自身职责。 | 明确 AI 的辅助定位；对关键决策提供依据、限制和人工判断要求。 |

## 二、AI 方案全生命周期质量与工程保障

| 风险 | 简要说明 | 风险化解方向 |
|---|---|---|
| 结果不准确或产生幻觉 | 输出听起来合理但与业务事实、数据或规则不符。 | 使用可信数据和业务工具支撑结果；显示依据和不确定性，并对关键结果进行验证。 |
| 检索内容不完整或过期 | Agent 找不到相关知识、引用错误版本或使用失效信息。 | 管理知识来源、权限、版本和更新责任；评估检索质量并处理过期内容。 |
| 用户或租户之间数据隔离失效 | 设计或实现缺陷导致检索、缓存或工具调用访问到其他用户或租户的数据。 | 在架构和工程实现中建立并验证端到端的数据隔离边界。 |
| 请求进入错误的处理路径 | 确定性的请求被送入 AI，或 AI 请求绕过预期的编排和控制流程。 | 在架构和接口设计中明确请求类型与路由规则，并验证路由边界。 |
| 多步骤推理或执行累积错误 | 单个步骤的偏差在计划、工具调用和后续执行中逐渐放大。 | 拆解任务并校验关键中间结果；限制执行循环，异常时暂停或转交人工。 |
| 质量无法稳定复现 | 相同任务因模型、提示词、上下文或工具变化而产生不同结果。 | 对模型、提示词、工具和知识版本进行管理；维护代表性评估集并进行回归测试。 |
| 评估未覆盖真实风险 | 离线测试或总体平均分掩盖长尾、高影响、特定提示词或特定用户群体的问题。 | 以真实任务和风险等级分层评估；结合试点、线上指标和用户反馈持续校准。 |
| 服务不可靠或依赖不可用 | 模型、检索、工具或业务服务故障导致任务中断或结果不完整；或者因为模型变化导致服务结构不稳定，模型不稳定导致整体服务不可用。 | 设置超时、熔断、健康监控和安全失败路径；保留可用的传统流程或人工处理方式。 |
| 响应延迟影响工作流 | 推理或多次工具调用耗时过长，造成等待、超时或重复提交。 | 定义端到端延迟预算；按需采用流式响应、异步任务和进度查询。 |
| 费用或资源消耗失控 | 长上下文、重复推理、Agent 循环或高并发导致成本和容量不可控。 | 设置预算、配额、并发和调用次数上限；监控单任务成本并对异常消耗告警。 |
| 超时、重试或部分失败造成错误副作用 | 多步操作中发生超时或失败，可能导致重复执行、部分完成或业务状态不一致。 | 明确操作状态和失败语义；对有副作用的操作保证幂等或提供安全恢复方式。 |


## 三、身份、授权与审批

| 风险 | 简要说明 | 风险化解方向 |
|---|---|---|
| 把“来自 AI”当成可信身份 | 客户端标记、提示词或模型自述被当成身份凭据或授权依据。 | 基于认证凭据识别用户和 AI 工作负载；不信任可由客户端任意设置的身份标记。 |
| 用户身份与 AI 身份混淆 | 无法区分谁提出请求、哪个服务执行操作，导致权限扩大或事后无法追责。 | 同时保留发起用户与 AI 工作负载身份，并在下游调用和审计中传递可信上下文。 |
| AI 获得超出任务需要的权限 | 服务账号权限过宽，或 AI 间接获得用户本身不具备的访问能力。 | 采用最小权限和逐资源授权；评估 OBO 等委托授权方式，并限制令牌范围、受众和有效期。 |
| 只在入口认证，未在操作处授权 | 用户通过登录或网关检查后，下游仍可能访问无权操作或其他用户的资源。 | 由拥有业务资源的服务对每个操作和目标资源进行授权校验。 |
| 将用户审批等同于权限 | 用户点击批准后，系统未确认该用户确实有权执行该操作。 | 将身份认证、权限授权和风险审批分开处理；执行前分别校验。 |
| 审批与实际执行内容不一致 | 用户批准的是概括性意图，实际执行时目标、参数或影响范围已经变化。 | 审批时展示具体操作、资源和参数；将批准绑定到该操作，并在变更或过期后重新审批。 |
| 高风险操作缺乏人工把关 | Agent 自动执行不可逆、高影响或涉及外部主体的操作。 | 按业务风险、影响和可逆性配置审批策略；对适用操作采用人工确认、限额或双人复核。 |

## 四、运营、安全与治理

| 风险 | 简要说明 | 风险化解方向 |
|---|---|---|
| 敏感数据被不当使用或泄露 | 个人、商业或受监管数据进入模型、检索、日志或不适当的用户会话。 | 实施数据分类和最小化；明确供应商、区域、训练使用、保留和删除规则，并进行脱敏与访问控制。 |
| 提示注入或恶意内容诱导非预期行为 | 用户输入或外部内容诱导 Agent 泄露信息、越权调用工具或执行非预期操作。 | 将外部内容视为不可信，并限制 Agent 可调用的工具和权限。 |
| 审计记录不足或过度记录 | 既可能无法还原决策与执行，也可能因记录完整提示词而扩大隐私风险。 | 记录必要的身份、请求关联、策略、审批、工具调用和结果；制定脱敏、访问和留存策略。 |
| 工程控制失效未被及时发现 | 数据隔离、授权、质量或资源限制等控制即使在设计和实现中建立，也可能因配置或运行环境变化而失效。 | 建立针对关键控制的运行监控、告警和定期验证。 |
| 提示词、知识和工具缺乏维护 | 业务变化后，提示词、知识库、策略或工具接口仍未更新。 | 为各类资产明确业务与技术负责人、版本、复核周期和退役方式。 |
| 线上异常无法及时止损 | 错误执行、数据泄露或质量突降发生后，团队没有明确响应流程。 | 建立监控告警、事件分级和响应预案；支持暂停工具、撤销凭据、回滚及人工接管。 |
| 用户支持无法处理 AI 特有问题 | 服务台无法区分模型错误、数据问题、权限拒绝或业务系统故障。 | 定义问题分类、诊断信息和升级路径；培训支持团队并提供可追踪的请求标识。 |
| 知识产权和内容来源不清 | 输入、检索或生成内容可能涉及未授权材料或不清晰的使用权。 | 审核数据和模型条款；保留来源信息，对高风险输出设置引用和人工审查。 |
| 供应商或第三方变化影响服务 | 模型服务的价格、条款、可用性或能力变化影响业务连续性。 | 管理供应商风险和变更通知；评估替代能力、数据可迁移性和退出方案。 |

## Agentification 风险控制原则

- **从业务价值出发，而不是从模型或 Agent 能力出发。** 只有在目标、收益和适用范围明确时，才扩大智能化投入。
- **让 AI 参与程度逐步增加，不让执行权限自动随之增加。** 自主能力与操作权限分别按业务风险、影响范围和可逆性评估。
- **确定性工作继续由确定性业务能力处理。** AI 主要承担意图理解、信息整合、推理和流程编排；通过明确路由选择合适执行路径。
- **复用并守住业务能力边界。** Agent 调用现有平台能力，不在提示词中复制业务规则；业务服务负责最终校验和副作用。
- **AI 操作可控、可确认、可追责。** 结合用户与 AI 双重身份、逐资源授权、风险审批和审计机制控制行动。
- **把失败、维护和退出纳入设计。** 对不确定、超时、依赖故障和异常行为设置暂停、澄清、转人工或回滚路径。
- **以持续证据推动能力演进。** 通过代表性评估、线上监控、事件复盘和变更治理，决定能力是否扩大、调整或退役。

平台Agentic是一个新的事物，对设计、开发、测试、运维、运营等全生命周期都提出了挑战，并非加一个新特性这么简单，软件的整个生命周期都需要积极考虑并提供相关对策。工程设计与实现负责建立可靠的隔离、授权和失败边界；运维侧负责监控其持续有效并在异常时响应，运营要分析相关数据，并对版本对迭代、特性演进或者退出提供输入反馈。具体的请求路由、OBO、审批策略、评估方法和事件响应等机制在后续专题中进一步分析。
